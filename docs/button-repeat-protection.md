# Захист від повторних дій

## Автоматичний захист за замовчуванням

Vite-плагін `scripts/ui-action-guard-plugin.mjs` автоматично обгортає `onClick`,
`onDoubleClick` і `onSubmit` (також capture-варіанти та JSX-spread) у коді
застосунку. Він підключений до dev, production та обох конфігурацій Vitest.
Залежності, сам runtime і тести не переписуються. Новим кнопкам і формам не
потрібно імпортувати hook чи додавати прапорець блокування:

```tsx
<Button onClick={save}>Зберегти</Button>
<button onClick={() => void upload()}>Завантажити</button>
<form onSubmit={async event => {
  event.preventDefault()
  await save()
  await refresh()
}} />
```

Спільний runtime `src/shared/ui/action-guard/uiActionGuard.ts` синхронно
блокує повторний запуск на тому самому елементі або формі, поки тривають
асинхронні завдання. Він відстежує повернений Promise, а також результати
відкинутих викликів (`void work()` і `work()`) у синхронно викликаних допоміжних
функціях. Це зберігає захист і тоді, коли обробник не повертає Promise явно.
Для кількох паралельних завдань блокування знімається після завершення всіх.
Синхронні перемикачі й навігація не отримують штучної затримки.

Повторні кліки та submit скасовуються до виклику обробника. Інтерфейс отримує
`aria-busy`, `aria-disabled` і `data-ui-action-pending`. Поля форми залишаються
увімкненими, тому склад `FormData` не змінюється; кнопка скасування та інші
незалежні дії доступні. Помилки, які обробник не перехопив, передаються до
`reportError` (або console.error), а блокування знімається.

Життєвий цикл операції має бути представлений Promise. Таймери, навмисно
відокремлені фонові завдання та сторонні бібліотеки, які приховують асинхронну
роботу і не повертають її Promise, потребують власного керування станом.
Блокування не переноситься на інший екземпляр елемента після remount.

## Явні захисні механізми для складних операцій

Наявні hooks залишаються додатковим захистом доменних операцій, зокрема для
викликів поза UI-подією або взаємного блокування кількох різних кнопок.

Кнопки асинхронних операцій мають блокувати повторний запуск до першого `await`,
а не покладатися лише на React-стан `loading`. Це стосується також `onSubmit`:
відключення кнопки саме по собі не є перевіркою всередині обробника.

## Форма з прапорцем зайнятості

`src/shared/hooks/useBusyState.ts` повертає стан для інтерфейсу, setter і
синхронний `tryStart`. Виклик `tryStart` одночасно захоплює блокування та вмикає
індикатор. Всі дії зі спільним станом зайнятості використовують те саме блокування.

```tsx
const [saving, setSaving, tryStartSaving] = useBusyState()

async function submit(event: FormEvent<HTMLFormElement>) {
  event.preventDefault()
  if (!isValid() || !tryStartSaving()) return
  try {
    await save()
    await refresh()
  } finally {
    setSaving(false)
  }
}
```

Існуючий `loading={saving}` або `disabled={saving}` залишається на кнопці.
Не скидайте стан зайнятості, поки ще виконується операція. У `useCallback`
додайте `tryStartSaving` до залежностей.

## Стан у reducer або батьківському компоненті

`src/shared/hooks/useSingleFlight.ts` захищає весь обробник, включно з його
наступними запитами, оновленням інтерфейсу та повідомленнями. Повторний виклик
із тим самим ключем отримує поточний Promise. Для кожного ключа має бути один
тип результату та одна логічна дія. Різні ключі й різні екземпляри компонента
незалежні.

```tsx
const runActionOnce = useSingleFlight()

async function submit(event: FormEvent<HTMLFormElement>) {
  event.preventDefault()
  return runActionOnce('submit', async () => {
    // Існуюча валідація, reducer, API-виклики та обробка помилок.
  })
}
```

`preventDefault` виконується для кожної події, включно з повторною. Блокування
знімається після успіху або помилки без таймера чи автоматичного повтору запиту.
Скасування застарілих пошукових запитів і переходів між даними зберігає свою
окрему семантику; їх не треба механічно перетворювати на одноразові дії.

## Перевірка

- `npm run test:action-guard`: виконання трансформованого JSX і runtime-тести
  звичайних кнопок, Mantine, меню, spread-props, форм, помилок та повторної спроби.
- `tests/browser/ui-action-guard.html`: локальний стенд з керованими Promise
  для подвійного кліку й Enter у браузері, без записів до API.
- Unit-тести обох hooks: повторний виклик до рендеру, помилка, повторна спроба,
  незалежні форми, багатокрокова операція й одноразові побічні ефекти.
- `OnlineShopCitiesPage.test.tsx`: реальна форма створення міста, подвійний клік
  і десять повторних submit під час незавершеного запиту.
- Регресійні тести змінених форм і перевірка TypeScript.

У тестах послідовні незалежні кліки розділяйте `await act(async () => { ... })`
або використовуйте `await user.click(...)`: між реальними подіями браузер виконує
мікрозавдання завершених Promise. Повторні кліки під час незавершеного запиту,
навпаки, надсилайте до його завершення й перевіряйте кількість викликів.

Це захист від повторних дій у поточному екземплярі інтерфейсу. Гарантія від
повторного виконання після перезавантаження, з іншої вкладки або після втрати
відповіді залежить від серверної ідемпотентності та існуючих механізмів
відновлення конкретної операції. Ця зміна їх не замінює.
