# QA модуля «Послуги»: постачальники послуг

Дата зрізу: 24.07.2026.

## Обсяг першої ітерації

Еталонний вертикальний зріз — `/accounting/supplier-organizations`:

- реєстр і пошук постачальників;
- створення, читання, редагування та видалення постачальника;
- створення й редагування договорів;
- завантаження та логічне видалення документів договору;
- експорт реєстру;
- довідники валют і організацій;
- взаєморозрахунки постачальника.

Маршрут `/service/organisations` є окремим read-only екраном взаєморозрахунків і не має контракту CRUD у поточному frontend-репозиторії.

## Матриця API

| Операція | Метод і endpoint | Автотест | Захист вхідних даних |
|---|---|---:|---|
| Список | `GET /supplies/organizations/all/search` | так | `limit > 0`, `offset >= 0`, коректний діапазон дат |
| Пошук | `GET /supplies/organizations/all/search` | так | trim пошуку та `organizationNetId`, валідація пагінації |
| Картка | `GET /supplies/organizations/get` | так | непорожній `netId`, фільтрація невалідної відповіді |
| Створення | `POST /supplies/organizations/new` | так | обов’язкова непорожня назва |
| Оновлення | `POST /supplies/organizations/update` | так | назва та `Id` або `NetUid` |
| Видалення | `DELETE /supplies/organizations/delete` | так | непорожній `netId` |
| Експорт | `GET /supplies/organizations/document` | так | trim пошуку, діапазон дат |
| Новий договір | `POST /supplies/organizations/agreement/new` | так | назва, постачальник, організація, валюта, дати |
| Оновлення договору | `POST /supplies/organizations/agreement/update` | так | ті самі поля плюс `Id` або `NetUid` договору |
| Валюти | `GET /currencies/all` | так | нормалізація колекції |
| Організації | `GET /organizations/all` | так | нормалізація колекції |
| Взаєморозрахунки | `GET /accounting/cashflow/get/filtered` | так | `netId`, дати, тип платіжного завдання |

Окремого endpoint для фізичного видалення договору в наявному контракті немає. Документ договору видаляється через `agreement/update` з `Deleted: true`; вигадувати новий DELETE-контракт на frontend не можна.

## Що стабілізовано

- Валідація назви й email показується безпосередньо біля поля.
- Значення очищаються від випадкових пробілів перед відправленням.
- Договір не зберігається без організації або валюти.
- Перевіряються неіснуючі календарні дати та порядок `Діє з` / `Діє до`.
- Договір із `NetUid`, але без числового `Id`, коректно йде в update, а не створює дубль.
- Паралельні multipart-мутації договору блокуються локальним mutation guard.
- Якщо create постачальника успішний, але backend не повернув `NetUid`, форма повертає користувача до списку і не провокує повторне створення дубля.
- Object-відповіді підтримують прямий формат і поширені обгортки `Item` / `Data`; явно невалідні записи не потрапляють у форму.

## Live QA перед релізом

Для цих перевірок потрібні авторизований dev-стенд і тестовий backend:

- створити постачальника, пройти всі чотири вкладки та повторно відкрити картку;
- перевірити 400/409/500 для create, update і delete — форма не повинна закриватися або показувати success;
- двічі швидко натиснути save для постачальника й договору — у БД має бути один запис;
- створити договір із файлами, додати файли при update, видалити один документ і перевірити, що решта не загубилися;
- перевірити reversed date range в договорі, списку та взаєморозрахунках;
- видалити тестового постачальника й переконатися, що запис зник зі списку та недоступний через `get`;
- перевірити експорт при порожньому результаті й при помилці генерації документа;
- перевірити права Add/Delete та недоступність мутацій для ролі без permission key.

Server-side DTO/DB-валідатори треба перевіряти в backend-репозиторії окремо: цей workspace містить лише React-клієнт.
